## 1. 项目一句话介绍

“塔罗之光”是一个基于 Taro、React 和 TypeScript 的塔罗牌 H5/微信小程序应用。用户可以选择牌阵、输入问题、完成抽牌并查看牌义和行动建议；在 H5 线上版本中，还可以通过独立的 Node 服务调用 DeepSeek 生成个性化解读和整体总结。

适合面试时的定位：这是一个同时涉及跨端前端、状态管理、离线 fallback、AI 服务端代理、Caddy 反向代理和 Windows 自动部署的完整小型应用。

## 3. 项目背景与目标

### 用户流程

1. 首页选择快速抽牌、基础牌阵、经典牌阵或主题牌阵。
2. 输入问题，或选择不输入问题直接随机抽牌。
3. 洗牌页展示抽牌过程和引导。
4. 结果页展示牌面、正逆位、关键词、牌义、牌位含义和行动建议。
5. 用户可以展开基础整体解读，或按需请求 AI 深度解读/AI 总结。
6. 有 Supabase 配置时保存和查询历史记录；未配置时仍可完成核心占卜流程。

### 核心价值

- 把一次抽牌过程组织成“问题—牌位—牌面—建议”的可理解流程。
- AI 输出用于自我反思和行动规划，不做确定性预测，也不替代医疗、法律或投资建议。
- 在后端尚未配置云数据库时，前端仍能通过本地数据完成演示和验收。

## 7. 关键问题与解决方案

### 7.1 “塔罗数据未加载完成”

原因是 Supabase 项目尚未创建，前端启动时无法拿到远程牌库/牌阵。

解决方式是 `src/db/api.ts` 先判断 `hasSupabaseConfig`：没有 URL 和 anon key 时直接使用 `localTarotCards`、`localSpreadTypes`；有配置时才请求 Supabase。这样核心抽牌不依赖外部数据库。

### 7.2 H5 桌面端和手机比例不一致

原因包括 viewport 配置不完整、Taro 的设计宽度换算和滚动容器高度不稳定。

处理方式：统一 `designWidth: 375` 和设备比例，在 `src/index.html` 补充移动 viewport，在全局样式中启用 `box-sizing`、最小高度和滚动约束，并用 `max-width`/响应式内边距限制桌面内容宽度。

### 7.3 构建成功但页面空白

曾出现 Taro 日志显示成功，但只生成 4 个模块和约 1 KB JS，实际是空壳 H5。

现在部署脚本不只检查命令退出码，还检查预构建包中的 `index.html`、CSS、`js/app.*.js` 和最大 JS 文件大小；不满足条件就停止并保留原站点。最终采用仓库内 `server/taluo-site.zip`，并用 SHA-256 校验包完整性。

### 7.4 Windows PowerShell 脚本乱码/解析失败

中文字符串被错误编码后，单引号和双引号边界被破坏，出现“字符串缺少终止符”等 ParserError。部署脚本中的机器可执行内容改成 ASCII，日志和错误信息也使用英文，减少编码依赖。

### 7.5 AI 失败或密钥泄露风险

浏览器不直连 DeepSeek。浏览器只请求 `api.taluo.lydiaowo.com`，Caddy 再转发到本机 `127.0.0.1:8790`；DeepSeek Key 通过服务器 `.env` 注入。

后端对请求体、牌面字段、AI JSON 结构进行校验，设置 85 秒上游超时；CORS 只允许配置的前端来源；同时设置单 IP 每分钟 12 次、单 IP 每日 20 次、全站每日 200 次配额，并把每日用量持久化到状态文件。

### 7.6 两个网站共用一台 Caddy

原有 `wbti.lydiaowo.com` 使用 `8787` 分析服务，塔罗新增静态站和 `8790` AI 服务。Caddyfile 采用追加独立站点块的方式，部署脚本先备份、再 validate、最后 reload；失败时恢复备份，避免影响原网站。

## 8. AI Prompt 演进

### 初版问题

初版要求单张约 200–300 字、总结约 300–400 字，容易输出冗长、逐张重复牌义、套话多，用户很难快速抓住重点。

### 当前策略

- 系统角色：有经验、真诚、克制的中文解读者。
- 顺序：先回应用户真正关心的问题，再解释牌位、正逆位和牌面关系。
- 结构：区分“牌面倾向—可能解释—现实行动”，矛盾牌面要说明拉扯和现实条件。
- 约束：单牌 100–160 字；整体总结 220–320 字；只返回 JSON，不返回 Markdown。
- 边界：不做绝对预测，不制造恐惧或依赖，不给医疗、法律、投资结论。

这类 Prompt 的关键不是堆砌形容词，而是同时约束角色、输入重点、输出 schema、长度和安全边界。后端仍会再次校验 JSON 和牌面数量，Prompt 不是唯一防线。

## 9. API 与后端设计

### 请求流程

```text
H5 result 页面
  -> src/db/interpretation.ts 组装 payload
  -> Caddy HTTPS /api/tarot/*
  -> 127.0.0.1:8790 server/index.mjs
  -> DeepSeek /chat/completions
  -> JSON 清洗与 schema 校验
  -> H5 展示
```

### 关键防护

1. 请求方法只接受 `POST`，并支持 `OPTIONS` 预检。
2. 请求体上限 80 KB，问题和牌阵名称分别截断为 500/100 字。
3. 牌面数量限制为 1–10，逐项清洗牌名、方向、关键词、牌义和建议。
4. 解析 fenced JSON 或混入文本中的 JSON，随后校验必需字段。
5. 使用 `AbortController` 设置 85 秒上游超时，统一返回用户可读错误。
6. API 响应设置 `no-store`、`nosniff`，CORS 使用来源白名单。
7. 额度预扣发生在调用模型前，避免无控制地消耗 DeepSeek 配额。

### 为什么使用 Node 原生 `http`

当前服务只有两个 POST 接口、一个上游调用和少量中间逻辑。原生 `http` 减少依赖、安装和 Windows 部署变量，足够满足当前规模；若未来增加路由、鉴权中间件、日志和测试，可迁移到 Fastify/Express，但迁移不是当前上线的必要条件。

## 13. 高频面试问题与参考回答

**问：为什么不把 DeepSeek Key 放前端？**

答：前端代码和 Network 请求都可被用户查看，放前端会导致密钥泄露、额度被盗刷和无法限流。因此前端只拿到自有 API 地址，密钥通过服务器环境变量注入，服务端再调用 DeepSeek。

**问：为什么使用本地 fallback？**

答：核心抽牌不应该被未创建的 Supabase 项目阻断。fallback 保证演示和线上基础流程可用，同时保留 Supabase 接入边界；等云项目创建后，数据层可以无缝切换到远程查询。

**问：如何保证 AI 返回格式稳定？**

答：Prompt 要求 JSON，调用时使用 `response_format: json_object`，服务端还会去除代码围栏、提取 JSON，并校验牌面数量、字段和非空文本。模型格式约束和后端校验是两层保障。

**问：为什么不直接用模型自由输出？**

答：自由文本不利于前端稳定渲染，也容易出现逐牌数量不一致。结构化 JSON 让每张牌和 summary 有固定位置，失败时可以明确提示并重试。

**问：如何控制 AI 成本？**

答：请求体限制、每分钟 IP 限流、单 IP/全站每日配额、上游超时和服务端 Key 隔离共同降低滥用风险；用量按日期持久化，重启不会立刻清零。

**问：如何解决桌面端和手机端比例问题？**

答：先检查 viewport、设计宽度和 Taro 单位换算，再限制内容最大宽度、统一 box sizing 和滚动容器高度，并用真实 H5 视口分别验收，而不是只看编译是否成功。

**问：为什么网站返回 200 仍可能空白？**

答：HTTP 200 只代表服务器返回文件，不代表 bundle 完整。曾遇到只产出 4 个模块、1 KB JS 的空壳构建，所以部署前增加入口、CSS 和 bundle 大小检查，并保留旧站点文件。

**问：如何让两个网站共用一台服务器？**

答：按域名分 Caddy site block，按端口隔离后端：wbti 继续使用 8787，塔罗 AI 使用 8790。部署脚本只追加塔罗块，先备份和 validate，再 reload。

**问：为什么选择 Node 原生 HTTP？**

答：当前只有两个接口，原生模块足够且依赖少、部署简单。接口数量和中间件复杂度增长后，再考虑 Fastify/Express，并以测试覆盖保证迁移行为一致。

**问：当前不足是什么？**

答：Supabase 云项目还未配置，历史记录无法在生产持久化；牌图依赖外部 CDN；限流状态是单机内存加本地文件，不适合多实例；AI 结果还需要更系统的评测集。下一步会先配置 Supabase 和数据迁移，再补 API/Prompt 回归测试、日志脱敏和多实例共享限流。

## 14. STAR 案例

### 案例：修复“构建成功但线上空白”

- **S（场景）**：Windows 服务器部署日志显示 Taro build 成功，但网站实际只返回空壳页面。
- **T（任务）**：在不影响现有 wbti 网站的前提下，阻止不完整构建覆盖线上文件。
- **A（行动）**：对比完整构建与异常构建产物，发现模块数和 bundle 大小明显异常；部署改为 checksum 校验的预构建包，并检查入口、CSS、app bundle 和最大脚本大小；失败时停止复制并保留旧文件。
- **R（结果）**：完整包才会进入 `C:\sites\taluo`，线上空白风险被前置到部署阶段；同样的检查也可迁移到 CI。

### 案例：把 AI 输出从“长而泛”改成“短而有逻辑”

- **S**：初版 Prompt 生成内容偏长，逐张重复牌义，用户不易找到行动重点。
- **T**：保留温和和安全边界，同时提升可读性与可执行性。
- **A**：明确角色、先回答问题、解释牌面关系、区分倾向/解释/行动；将单牌限制为 100–160 字、summary 限制为 220–320 字，并在后端做结构校验。
- **R**：实测三张牌输出为 139/150/142 字，summary 约 320 字，响应更直接且前端结构稳定。

## 15. 技术取舍与后续规划

### 当前取舍

- 本地 fallback 优先保证可用性，代价是生产牌库暂未由云端统一管理。
- 单机 Caddy + Node 适合当前访问量，代价是限流和用量状态不是分布式的。
- 原生 HTTP 减少依赖，代价是未来需要自行补更多中间件能力。
- 外部牌图 URL 减少仓库体积，代价是依赖第三方资源稳定性。

### 建议下一步

1. 创建 Supabase 项目，执行 migrations，配置 H5 的 URL 和 anon key。
2. 把历史记录、AI 请求成功率、延迟和配额使用接入可观测日志；日志中不记录 API Key 和完整用户问题。
3. 为 Prompt 和 JSON 校验建立固定测试样例，覆盖空问题、逆位、十张牌、矛盾牌面和模型异常返回。
4. 牌图下载到自有对象存储并加版本化，降低外部 CDN 风险。
5. 若流量增长，迁移用量状态到 Redis/数据库，并评估 Fastify、队列和多实例部署。
